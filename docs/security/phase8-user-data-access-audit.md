# Phase 8: user data access and ownership audit

Status: local implementation and test evidence. **Do not release before the offline ownership review below.** This audit was performed against the Phase 6 integration head (`9112aec`); Phase 7 changes must be rebased and checked separately.

## Ownership rule

- `users.google_id` is the stable account identifier. A populated `user_id` on an account-owned row takes precedence over its email, even if the email matches another account.
- An unbound legacy scan row may be read or erased by an account only when its email has exactly one canonical owner among **all** `users` rows, including inactive and deleted rows. The canonical key uses NFKC/casefold for the local part and UTS #46 IDNA for the domain. It does not infer provider-specific aliases (dots or plus tags).
- If uniqueness cannot be shown, the row is withheld. Logs contain only aggregate counts and table names, never addresses, QR text, wallet values, or account IDs. Administrative reads retain their existing role-gated bypass.
- Existing production rows that earlier startup code assigned with `LIMIT 1` are **not proven** just because `user_id` is populated. The offline audit must review and quarantine these before this code is deployed.

## Evidence and release gates

1. Run `scripts/security/email_ownership_dry_run.py` against an **offline, access-controlled production backup**. Review account collisions, email-only rows, mixed wallet/fraud owner values, and every scan row that may have been assigned by the removed `LIMIT 1` startup backfill. Do not run a blind SQL merge or edit live production data from this branch.
2. Quarantine or manually attribute uncertain ID-bound rows from the earlier backfill. Until this is done, an ID value alone is not proof of historical ownership, so Phase 8 must remain unreleased.
3. Replace email-keyed `scans`, `scan_events`, wallets, nonces, referrals and fraud state with account-ID keys using an explicit reviewed migration. Add a unique canonical account-email index only after collisions are resolved. The current uniqueness check scans `users` and is intentionally conservative; it is not a long-term performance design.
4. Complete privacy erasure/export mapping for retained uploads, subscriptions, payment references, consent/audit records and external data processors. The public route deliberately keeps requests pending until that review; a separate verified completion workflow is required.
5. Recheck the Phase 7 Go Ghost and Turnstile changes after integration. Verify the final route stores only stable owner IDs and does not expose a job by a user-supplied ID.
6. Review the public leaderboard after migration. It now withholds all unbound legacy activity; restored historical scores require manually reviewed ownership. The old email `OR` joins must not return.

Focused regression tests cover two concurrent sessions with a colliding email, unique legacy access, admin bypass, privacy export refusal, foreign ID-bound erasure preservation, wallet gating, fraud score isolation, and unchanged normal wallet use. No production database or third-party service was accessed.
