# UI polish research log

Researched 2026-11-14 against the UI plan at commit `83eed0a`. These are implementation decisions for Phases 1–8, not claims that the current UI already meets them. Links point to the original standards, design systems, and framework documentation.

| Topic | Primary source (accessed 2026-11-14) | Evidence and decision |
| --- | --- | --- |
| Spacing | [IBM Carbon spacing](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview) | Carbon uses named tokens and 2, 4, and 8 px increments, with larger steps for layout. Keep the plan's 2–96 px scale and semantic aliases. Its 20 px intermediate step is a local choice, not a Carbon token. Use `clamp()` only where the design should respond to viewport width, as in page gutters. |
| Empty states | [IBM Carbon empty states](https://www.carbondesignsystem.com/building-blocks/core/patterns/empty-states) | Distinguish first use, no results, and unavailable content. Name the missing content, explain the next step, and offer a relevant action. A dense table may use a compact text state; an illustration is optional. Do not call a failed request “no data.” |
| Loading patterns | [IBM Carbon loading](https://www.carbondesignsystem.com/building-blocks/core/patterns/loading) | Use skeletons where the final row or card shape is known. Use an inline indicator on a button's own action and progress text for a multi-stage scan. Avoid skeletons for buttons, menus, and modals, and avoid a spinner that hides existing content. |
| Loading timing | [Nielsen Norman Group response-time limits](https://www.nngroup.com/articles/response-times-3-important-limits/) | Rough human-perception limits are 0.1, 1, and 10 seconds. The plan's 300 ms delay is a reasonable local anti-flicker default, not a standard. After about 10 seconds, say the work is still running. The 15-second timeout is also a local default: apply it only to cancellable asynchronous requests with a known server budget; a full-page POST or a scan still running on the server must not be presented as definitively failed merely because a client timer fired. |
| Live loading announcements | [WAI-ARIA 1.2 `aria-busy`](https://www.w3.org/TR/wai-aria-1.2/#aria-busy), [WCAG 2.2 status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | Mark the changing region busy until its update is complete. Announce the start of a meaningful wait once through a polite status region; reserve assertive alerts for actionable failures. Do not repeatedly announce every skeleton row or scan step. |
| Field errors | [GOV.UK error message](https://design-system.service.gov.uk/components/error-message/), [WCAG 2.2 error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html), [error suggestion](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html) | Identify the field, describe the problem in text, and give a correction when known. Keep the user's entered values. Link inline text to its control with `aria-describedby` and set `aria-invalid` on invalid controls. Authentication errors can remain deliberately vague. |
| Error summary | [GOV.UK error summary](https://design-system.service.gov.uk/components/error-summary/) | **Change from plan:** show a focused summary for a failed form submission even when only one field failed. GOV.UK's tested pattern includes both a summary and a linked inline error for any validation failure; the plan's “two or more” threshold is less clear for keyboard and screen-reader users. The summary and inline text should match. |
| Error responses | [FastAPI exception handlers](https://fastapi.tiangolo.com/tutorial/handling-errors/), [MDN 404](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/404), [MDN 503](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/503), [Google crawler status guidance](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) | FastAPI supports custom exception handlers, so browser routes can render HTML while API routes keep JSON. Preserve the actual 4xx/5xx status; an error-looking `200` can be treated as a soft 404. Give a useful recovery action, no-index and no-store on error pages. A 503 may include `Retry-After` when a retry time is known. |
| Rate limits | [MDN 429](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429), [Retry-After](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After) | Use status 429 and `Retry-After` when the server knows the delay. A client countdown is advisory and must not bypass server enforcement. Handle both seconds and HTTP-date forms if the UI reads the header. |
| API errors | [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) | Problem Details standardizes `type`, `title`, `status`, `detail`, and `instance`, with extension members. Keep SafeScan's existing JSON `error` string and media type for mobile compatibility. Add `code`, `hint`, `field`, and `request_id` beside it. Do not advertise `application/problem+json` or claim RFC 9457 conformance unless a later version implements its full shape and client negotiation. |
| Touch and motion | [WCAG 2.2 target size minimum](https://www.w3.org/TR/WCAG22/#target-size-minimum), [target size enhanced](https://www.w3.org/TR/WCAG22/#target-size-enhanced), [W3C animation guidance](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html) | WCAG AA's minimum is 24×24 CSS px with exceptions; 44×44 is the enhanced AAA target. Keep 44×44 as SafeScan's usability goal without calling it the AA requirement. Disable unnecessary motion when the user requests reduced motion. |

## Codebase findings to carry into implementation

Inspected `templates/`, `static/*.js`, `hackabull/routes_*.py`, `hackabull/app_module.py`, and `hackabull/security.py` at `83eed0a`.

- The home page has a scanner and a result **dialog in the same `index.html` template**. The result is not a separate URL. It has a special incomplete-verification state that must never be described as safe.
- `history.html` renders signed-out and first-use branches on the server. `history.js` also fetches `/api/history` for signed-in history. `leaderboard.html` renders initial data but `leaderboard.js` refreshes it and silently swallows failures. `malicious_database.html` has distinct loading, no-data, no-match, and error text in `malicious-database.js`.
- Go Ghost is available to guests as well as signed-in users. It has account/session notices, a local profile form, per-broker progress, and no-match handling. Its data is intentionally browser-local; state-component work must not transmit profile fields for screenshots or telemetry.
- `generate_qr.html` has an inline error and a hidden generated-result area. `profile.html`, `login.html`, `history.html`, `leaderboard.html`, and `malicious_database.html` each carry a `<style>` block. Some templates also carry inline `style=` attributes. Phase 2 should move these with screenshot review.
- Admin uses one `admin_shell.html` template with branches for dashboard, users, scans, waitlist, reports, blocklist, airdrop queue, fraud, audit/activity logs, API keys, and settings. Empty tables usually show headings only; waitlist alone has a “No waitlist signups found” line. `/admin/risk-logs` reuses the scans branch. `/admin/airdrop/wallets` reuses the airdrop branch.
- The user drawer and data-processing/consent/breach pages use `admin_shell.html` or `admin_table.html` but are not the same table branches. Treat them as distinct views in the state inventory.
- The admin user drawer route sets `page='user_drawer'`, but `admin_shell.html` has no corresponding branch. Its current HTTP 200 view has an empty main panel; include a real drawer/content state when that view is polished.
- Current `fetch(` sites include wallet/referral, QR generation, Go Ghost, report/consent, leaderboard, malicious database, history, admin user search, runtime, camera telemetry, and decoder options. The last two are low-level background requests; a blanket “all fetches through `UIStates.fetchJson`” rule would be inappropriate. Every user-facing failure still needs a visible outcome.
- `app_module.py` central exception handlers return JSON for every request today. Some route and middleware errors return JSON directly, so Phase 4 needs both exception-handler and direct-response audits. `app-core.js` still has five `window.alert` calls, while `qr-camera.js` has intentionally ignored telemetry failures; Phase 5 must distinguish critical user actions from optional counts.

## Deferred validation

The screenshots in Phase 0 show current content and signed-out/first-use states. Loading, failed-network, scan-result, generated-QR, and destructive admin outcomes need deterministic fixtures before complete before/after visual coverage is possible. A future `?__state=` switch must be gated by `MOCK_MODE` and proven inert outside that mode as required by the plan.
