# Privacy operations: Phase 4 implementation status

**ATTORNEY REVIEW NEEDED.** This is an engineering record, not an approved privacy notice. Field-level legal bases and retention, billing records, backups and public policy reconciliation remain open.

## Changes in this branch

- New web scan history, scan-event references, recent-scan counters and fraud references keep the URL scheme, host and path, but drop query and fragment. This can collapse two URLs that differ only by query into one unique scan. The immediate scan response and security checks still use the full input URL.
- The result cache uses a keyed HMAC of the full URL so lookup remains exact without storing the URL. Old raw-URL cache rows are purged on schema initialization; cached results older than 24 hours are deleted.
- A startup scrub removes old query-bearing or private payload references from scan history, scan events, aggregate scan URL lists and velocity rows. It keeps aggregate scan counts. Existing scan events with a raw query are discarded, so a later scan can create a new event. The scrub is idempotent; it does not erase SQLite pages or backups already made before the deployment. Those require a storage/backups retention review.
- Consent-log rows older than five calendar years are deleted at startup and daily. The five-year period is already stated in the current public policy; it is not a conclusion about a legal requirement. Set `RETENTION_LEGAL_HOLD=true` during a documented investigation to pause this deletion. This flag does not stop disposable cache expiry.
- Browser Global Privacy Control suppresses optional first-party scanner performance counts even after a previous `all` choice. A `Sec-GPC: 1` request is discarded at the telemetry endpoint before parsing or counting; the consent endpoint records `essential_only` rather than `all` or `custom`. This is a conservative engineering response, not a determination that SafeScan sells or shares personal information or that any jurisdiction's GPC obligations are met. Counsel must assess applicability and deployed headers.
- Proposed Cookie Policy v1.1 lists current first-party cookie and browser-storage key families, with archived v1.0 and v1.1 snapshots and an exact table/inventory/source regression gate. The table is a counsel-review draft; representative guest browser behavior is tested, but provider cookies, signed-in/admin/payment flows and production browser traffic still need verification.

## Data rights behavior after Phase 4B

- A signed-in user whose account is the unique owner of the email can export account, scan, Go Ghost, age, wallet, Discord, session metadata, consent, waitlist, report and billing rows linked to that account. The portal shows the JSON and offers a signed-in POST download with `no-store`; it never accepts the email from the download form. Credential hashes, raw session IDs, challenges, anti-abuse details, retained QR images and third-party referral addresses are withheld. The response lists the affected categories under `manualReview`; requests with those rows stay `submitted` while the partial export is visible to the signed-in user. A duplicate account email prevents any self-service export.
- A signed-in user can correct only their own `display_name` automatically. Provider email/identity, wallet, age, payment and other fields remain `submitted` for manual review. The request form has explicit correction fields; free-text details are not treated as authorization to change account identity.
- An erasure request for a unique account leaves every row intact when payment records, consent proofs, audit/security evidence, reports, referrals, uploads, suppressions, prior requests or a legal hold require review. The account and sessions remain available for subscription cancellation. The DSR stays `submitted`, not completed. With no such blockers, the flow removes directly linked account, session, age, wallet, device, Discord, local credential, waitlist, scan and Go Ghost rows and marks the DSR completed. A minimal request record and audit event are created *after* erasure for operational proof; this exception requires counsel review and public disclosure.
- Ambiguous ownership also stops all erasure before any deletion. The request remains pending for an operator; do not claim that submitting a request means all copies have been deleted.

## Unfinished data rights and retention work

- Some source tables have no stable owner (`stripe_webhook_events`, `scan_results`, `age_denials`, guest tickets, global caches and breach summaries). Correlating them to an individual needs a reviewed matching design. Stripe-hosted data, uploads, historic backups and security evidence still need an operator workflow. Counsel must decide whether to retain or anonymize billing consents, receipts, fraud evidence and audit trails after a request. `docs/legal/data-map.yaml` assigns each table a `rights_class` to track this decision.
- The public policy says inactive accounts are deleted after two years, but there is no safe account-deletion scheduler. Do not add one until active subscriptions, wallet and Go Ghost records, legal holds, backups and identity verification are resolved. Revise the public promise with an archived version and attorney review if the job cannot be delivered.
- `docs/legal/data-map.yaml` lists every schema field and a table-level rights treatment. It does not identify every field's legal basis or exact retention. It is not yet suitable as the single source for the public policy or admin processing log. The table/column drift test must remain green as fields are added.
- `url_reports`, public blocklist entries, other users' referral rows, fraud metadata and historic backups may still contain query strings or personal details. They need separate evidence and ownership rules. The listing dispute phase should handle reported URLs without overbroad blocklist matching.
- A 45-day target can be shown to admins after the owner and counsel choose which request categories and jurisdictions use it. Do not present it as a universal deadline. Requests from unauthenticated email addresses remain pending; an email match alone is not ownership proof.
- Data sent to Google Web Risk includes a scanned URL's full query when configured; the PhishTank feed is checked locally. A query can contain personal tokens. A provider-by-provider disclosure and contractual review are needed before a public privacy-table revision. See `docs/legal/vendor-register.md`.

## Phase 1 integration

The rights flow is based on merged Phase 1 payment and age tables. The three Stripe tables, Solana references, age tables and new cookies are in the inventories. Any card billing record keeps the account and its session available for cancellation while a DSR is reviewed. See `docs/legal/phase-1-payment-release.md`.
